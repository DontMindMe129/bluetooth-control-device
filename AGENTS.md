# Bluetooth Control Device repository instructions

## Scope and development mode

- These instructions apply to the entire repository.
- Develop this firmware incrementally, one requested module at a time. Do not independently implement the complete product or add unrequested modules.
- The target is an STM32F103C8T6 Blue Pill development board. There is no custom PCB yet, so treat board-level assumptions beyond the stated pin allocation as unknown.
- The runtime is bare-metal STM32 HAL generated by STM32CubeMX; no RTOS is configured.
- PC communication currently uses plain UART through a USB-to-UART adapter. A Bluetooth UART module is a possible later addition, not a current dependency.
- Flashing and debugging use an ST-Link V2 probe through the STM32Cube ST-Link GDB Server interface in VS Code.

## Source of truth and investigation

Use the source appropriate to the claim:

1. User-approved module requirements and explicit user decisions govern intended behavior, timing, retries, timeouts, and reset policy.
2. `Bluetooth_Control_Device.ioc` is the CubeMX configuration source. Re-read it before work affected by pins, clocks, peripherals, interrupts, or code generation.
3. The current generated source, especially `Core/Src/main.c`, `Core/Src/stm32f1xx_hal_msp.c`, and `Core/Src/stm32f1xx_it.c`, governs what the firmware actually initializes and handles.
4. The current CMake files, presets, toolchain file, startup code, linker script, and shipped CMSIS/HAL headers govern the build and target details.
5. Use the exact STM32F103C8T6 datasheet, reference manual, and errata for device behavior, followed by official ST documentation and examples.
6. Use engineering inference only when necessary, label it clearly, and never use it to invent a required hardware or timing value.

When the `.ioc` and generated code disagree, identify the exact difference and its effect. Do not silently choose one side or modify protected configuration; ask the user when the difference materially affects the requested work. Re-read affected files after CubeMX regeneration rather than relying on earlier observations.

## Current configuration boundaries

Treat the following as intended resource allocation, not as proof that detailed peripheral configuration is final:

| Function | Resource |
| --- | --- |
| PC serial link | USART2 on PA2/PA3 through USB-to-UART |
| OLED | I2C1 on PB6/PB7 |
| ADXL345 | I2C2 on PB10/PB11, with EXTI on PA1 |
| DHT11 | TIM3 channel 4 input capture on PB1 |
| Servo/PWM output | TIM2 channel 1 PWM on PA0 |
| Buttons | PA4-PA7 and PB0 through EXTI |
| Five digital outputs | PB12-PB15 and PA8 |
| Heartbeat LED | PC13, active-low |

- Re-read the `.ioc` and generated source after every CubeMX regeneration before relying on the details below.
- The generated runtime currently uses HSI as the 8 MHz system clock. PD0/PD1 are reserved as HSE oscillator pins in the `.ioc`; do not infer that HSE is active.
- The five UI buttons on PA4-PA7 and PB0 are generated as falling-edge EXTI inputs with internal pull-ups. Their EXTI IRQs use preemption priority 1, subpriority 0.
- The ADXL345 interrupt input on PA1 is generated as EXTI1 with no internal pull and shares EXTI priority 1, subpriority 0.
- TIM3 input capture uses priority 0, subpriority 0. I2C1 event/error, I2C2 event/error, and USART2 use priority 2, subpriority 0. The corresponding generated IRQ handlers are present.
- SWD remains enabled on PA13/PA14, with JTAG disabled. Preserve SWD access unless the user explicitly approves a configuration change.

## Ownership and edit boundaries

- CubeMX owns the existing generated files under `Core/`, including `main.c`, MSP and interrupt files, HAL configuration, system support, and generated headers.
- In a CubeMX-generated file, edit only inside the matching `USER CODE BEGIN` / `USER CODE END` region. Ask before changing anything outside those regions.
- New project-owned `.c` and `.h` modules may be created when they belong to the requested incremental module. Keep their interfaces focused and avoid mixing unrelated device logic.
- `Drivers/` contains the vendor-supplied STM32Cube HAL/CMSIS code. Use it as a reference and dependency; do not modify it unless the user explicitly requests that scope.
- Ask before changing any of the following:
  - `Bluetooth_Control_Device.ioc`;
  - any CMake file or preset, including generated CMake content;
  - `STM32F103XX_FLASH.ld`;
  - `startup_stm32f103xb.s`;
  - CubeMX-owned configuration or generated text outside a matching user-code region.
- Do not assume the comment in the top-level generated-once `CMakeLists.txt` grants permission to edit it; the approval rule above controls this repository.

## Firmware design constraints

- Do not use dynamic memory allocation. Use statically allocated or fixed-capacity storage with explicit bounds; do not introduce `malloc`, `calloc`, `realloc`, `free`, or an allocator-backed abstraction.
- Keep project-owned firmware paths non-blocking. Do not use busy-wait loops, CPU polling for peripheral completion, blocking HAL calls, or delay-based coordination.
- Choose the architecture from the module and user-supplied requirements. Cooperative superloop steps, state machines, callbacks, interrupts, and DMA are options rather than universal defaults.
- Use interrupts where appropriate, keep interrupt work bounded, and defer longer processing to the main context.
- Make timing behavior explicit. Every wait, communication operation, and state transition that can stall must have a finite timeout defined by the relevant module requirements.
- On errors, perform bounded retries before reset. Retry counts, retry delays, timeout values, reset scope, and post-failure behavior must come from the relevant module requirements. If any required value is absent, ask a focused question rather than inventing it.
- Do not treat the current generated `Error_Handler()` infinite loop as a module-level retry or reset policy.
- Account for the STM32F103C8T6 memory limits reported by the current linker script: 64 KiB Flash and 20 KiB RAM. The generated linker script reserves heap space, but project code must still obey the no-dynamic-allocation policy.

## Build, verification, flash, and debug permissions

- Read-only inspection and consistency checks are allowed without approval.
- The configured build system is CMake 3.22 or newer with Ninja and the `arm-none-eabi-` GCC toolchain selected by `CMakePresets.json`.
- The canonical preset commands are `cmake --preset Debug` or `cmake --preset Release`, followed by `cmake --build --preset Debug` or `cmake --build --preset Release` for the matching configuration.
- Ask before running any CMake configure command or any build command, including the canonical commands above. Do not reuse or alter the existing `build/` directory as a substitute for approval.
- Ask before flashing the target or starting a hardware debug session.
- After an approved build, review compiler diagnostics and the linker memory-usage output. Match further verification to the changed module; report when required tools or hardware are unavailable instead of claiming success.

## Missing information and conflicts

- Investigate current repository files first when they can answer the question without changing state.
- Ask the minimum focused question when missing information affects pin safety, electrical assumptions, peripheral configuration, timing, protocol behavior, retry/reset policy, permissions, or success criteria.
- Stop before an unsafe, unauthorized, or misleading change. Do not fill consequential gaps with typical STM32 values or guessed module defaults.
- Distinguish current generated behavior, intended resource allocation, and future design plans in explanations and reviews.
